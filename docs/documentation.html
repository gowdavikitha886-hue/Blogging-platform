1. Overview

BlogSphere AI is a modern, responsive, AI-powered blogging platform. It began as a single dark-themed editor page and has been upgraded into a complete writing and publishing product with authentication, full blog CRUD, an AI writing assistant, SEO tooling, and writing analytics.

Per project requirements, the application keeps its original architecture — a self-contained client-side single-page application (SPA) with no external runtime dependencies. All logic, styling and data live in a few static files that run directly in the browser. This makes the project trivial to host (any static host) and impossible to break through missing install steps.

Zero dependenciesNo npm packages, no build step. Plain HTML/CSS/JS.
Real database-like storeVersioned schema in localStorage with migrations.
Secure authPBKDF2-SHA256 password hashing via WebCrypto + salted sessions.
AI, optionalBuilt-in offline assistant plus any OpenAI-compatible endpoint.

3. Architecture & file structure

BlogSphere AI is a client-only SPA. A hash-based router renders views into a single <main> element. All state lives in a versioned localStorage document managed by the BS core module.

├─ css/
│  └─ styles.css         # Design system: tokens, components, responsive, print

6. Migration from v1

The original app stored data under the key bsai with SHA-256 password digests. On first load, if no v2 document exists but a v1 document does, the platform runs migrate():

  • Users, posts, comments, likes and bookmarks carry over.
  • Legacy string password hashes are preserved in legacyHash.
  • Posts gain slug, tags, cover, seoTitle, seoDesc and publishedAt defaults.
  • On the user's next successful login the legacy hash is atomically upgraded to PBKDF2-SHA256.

7. Authentication & security

Registration & login

  • Registration validates name, unique email, 3–20 char username, 8+ char password and confirmation, with a recommended security question.
  • Login accepts either email or username.

Password hashing

Passwords are never stored in plaintext. Each password is hashed with PBKDF2-SHA256 using a random 16-byte salt and 150,000 iterations, via the browser WebCrypto API:

deriveBits(PBKDF2, salt=random16, iterations=150000, hash=SHA-256) → 256-bit digest

Verification re-derives the digest and compares. Recovery answers are hashed the same way.

Sessions

On login a random 24-byte token is issued with a 7-day expiry, stored as session { u, token, exp }. On every load the session is validated; expired sessions are cleared automatically.

Authorization

Every mutating operation checks ownership. Data.savePost, setStatus, deletePost and deleteComment reject actions where author/owner !== session user. Protected routes (dashboard, write, saved, settings) and guest-only routes (login, register, forgot) are enforced by router guards.

Scope & limitation: because this build intentionally remains client-side, hashing and sessions run in the browser and the AI key is stored locally. PBKDF2 with a per-user salt is the strongest available client-side scheme, but it does not protect against an attacker with direct device access. For multi-user production use, move auth and data to a server (see the roadmap). Never enter a real password you use elsewhere into a demo.

9. The editor

The editor is a contenteditable surface driven by document.execCommand with a sticky toolbar, plus a right-hand sidebar of widgets.

  • Header: back button, live status ("Draft"/"Published"), last-saved relative time, Focus, Preview, Save Draft, Publish.
  • Main: title (with n/120 counter), excerpt (with 120–160 char meter), toolbar, content area, sticky action bar with stats and a completion ring.
  • Publishing widget: category, tags, featured image (URL or upload to data-URL), cover preview.
  • SEO widget: SEO title + meta description with length meters, live score ring and a checklist.
  • AI widget: eight one-click tools (below).
  • Focus mode: hides the top bar and sidebar and centers a wider writing column.

10. AI assistant

The assistant works in two modes and chooses automatically.

Offline engine (default, no key)

  • Suggest titles — keyword-driven title templates.
  • Write excerpt — extractive 150-character summary.
  • Summarize (TL;DR) — extractive top-sentence summary.
  • Suggest tags — keyword frequency, matched against existing tags.
  • Generate outline — section outline from keywords.
  • Improve writing — readability-based tips.
  • SEO recommendations — from the SEO engine.
  • Proofread — double spaces, repeated words, long sentences, filler words.

Live mode (optional)

In Settings → AI assistant, provide an OpenAI-compatible base URL, API key, model and temperature. The app POSTs to {baseURL}/chat/completions:

POST {baseURL}/chat/completions
Authorization: Bearer <key>
{ "model": "...", "messages": [ {role:"system",...}, {role:"user",...} ] }

If the request fails (network, CORS or bad key) the app falls back to the offline engine and shows an error toast. A Test connection button verifies the endpoint. The AI badge shows Live or Offline.

CORS note: browsers block cross-origin requests unless the API sends the right CORS headers. Some providers allow this; others do not. If live mode is blocked, either use a provider that permits browser origins or proxy requests through your own backend.

14. Setup & running

There is nothing to install. Open index.html directly, or serve the folder over a local web server (recommended, so crypto.subtle and storage behave consistently).

Option A — double-click

Open index.html in Chrome, Edge or Firefox.

Option B — local server

# Python (pre-installed on most systems)
python -m http.server 5500
# then open http://localhost:5500

# or Node
npx serve .
# or
npx http-server -p 5500

First run

  1. Click Start writing / Create an account and register.
  2. Open Write, add a title and body — watch the stats and SEO score update live.
  3. Use the AI sidebar tools, then Save draft or Publish.
  4. (Optional) Home → Load sample articles to populate the feed.
  5. (Optional) Settings → AI assistant to connect a live endpoint.

16. Limitations & roadmap

  • Single device: data lives only in the browser's localStorage; it is not synced across devices.
  • Client-side security ceiling: hashing protects stored values but cannot fully defend against device-level access — a server is required for true multi-user security.
  • AI key exposure: live AI keys are stored locally and used from the browser; use a server proxy for production.
  • Storage quota: very large inline images (data-URLs) can approach the ~5 MB localStorage limit — prefer image URLs.
  • Email: no email service is wired, so password reset uses a security question instead of email links.

Suggested next steps: a Node/SQLite or hosted backend with server-side PBKDF2/bcrypt, JWT/session cookies, server-side rendering or an API-driven SPA, image uploads to object storage, email verification and reset links, and rate limiting.

17. Print to PDF

This document is print-optimised. To generate a PDF:

  1. Click the Print / Save as PDF button (top-right), or press Ctrl+P.
  2. Set Destination to Save as PDF.
  3. Choose Paper size A4, Margins Default, and enable Background graphics.
  4. Click Save.

The print stylesheet hides the print button, switches to a print-friendly palette and keeps tables, code blocks, cards and section headings from splitting across pages.
